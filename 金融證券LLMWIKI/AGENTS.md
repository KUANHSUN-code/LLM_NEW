# 金融證券法規 LLM Wiki 營運指引 (AGENTS.md)

本文件是本知識庫的最高架構與行為綱領（Schema）。它規範 LLM 如何作為專職的「金融證券法規研究助理與知識庫工程師」，與使用者（首席研究員 / PI）協同構建持久、互聯且具複利效應（Compounding）的學術知識庫。

---

## 1. 核心哲學與定位 (Core Philosophy)

1. **持久性知識資產，拒絕一次性拋棄**：
   傳統 RAG 每次查詢都從原始文件重新抽取碎片，無法累積全局理解。本專案以 **Karpathy LLM Wiki** 為藍本，將知識編譯進結構化、互相參照的 Markdown 網絡中。
2. **人機分工明確**：
   - **人類（研究者）**：負責選題方向、引導深度討論、提供研究材料、審查結論。
   - **LLM Agent**：負責所有繁重的文獻精讀、法理提煉、雙向鏈結（Cross-referencing）、多頁面連動更新、索引目錄與日誌簿記。
3. **Obsidian 為 IDE，Markdown 為代碼庫**：
   所有頁面皆以標準 Markdown 撰寫，全面採用 Obsidian 雙向鏈結 `[[頁面名稱]]` 與 YAML Frontmatter，確保 Graph View（關聯圖譜）與 Dataview 插件完美運作。

## 2. 目錄架構與三層權限 (Architecture & Boundaries)

```
金融證券LLMWIKI/
├── AGENTS.md                  # [Layer 3] 本規範文件（營運指引與 Schema）
├── index.md                   # [Layer 2] 內容總索引（依領域、法規、概念分類）
├── log.md                     # [Layer 2] 純追加操作日誌（Ingest, Query, Lint）

│   └── notes/                 # 原始剪藏筆記、法規公告、主管機關函釋原文
├── wiki/                      # [Layer 2] 知識網絡層（LLM 全權維護與更新）
│   ├── papers/                # 每篇論文的結構化精讀與蒸餾筆記
│   ├── regulations/           # 實體法規、條例、監理機關發布之指引規範實體頁
│   ├── concepts/              # 法律概念、法理學說、要件判定準則（如內線重大消息時點、Howey Test）
│   ├── cases/                 # 指標判決、實務裁判、主管機關行政處分裁罰案例

│   └── synthesis/             # 跨文獻深度綜述、研究趨勢、法制漏洞與待解爭點
└── assets/                    # 圖表與投影片資產（存放論文架構圖、統計圖表、簡報圖片）
```

## 3. 原始文獻處理守則 (Raw Papers Protocol)

針對文獻來源，LLM 必須嚴格遵守以下存檔規則：

1. **使用者在對話中提供/上傳 PDF 論文**：
   - LLM 必須立即將其完整保留/儲存至 `raw/papers/` 目錄中。
   - 檔名規範：`[年份]_[第一作者姓氏]_[論文精簡英數標題].pdf`（例如：`2024_Lin_Securities_Fraud_AI.pdf`）。
2. **使用者提供 arXiv 或線上學術論文連結**：
   - LLM 必須透過網路工具或下載指令，將該論文之原版 PDF 下載並存入 `raw/papers/` 中。
   - 若僅有網頁 HTML 或純文字，則轉換為標準 Markdown 儲存至 `raw/notes/`。
3. **不可變原則（Immutable Source of Truth）**：
   - 存入 `raw/` 之後的檔案為真實世界客觀依據，LLM 不得擅自修改或刪除原始檔案。

## 4. 三大核心標準作業程序 (Core Workflows)

### 作業一：文獻入庫與滾雪球連動 (Ingest Workflow)

每當有新論文進入時，執行以下 7 步標準作業：

1. **存檔與建立來源**：將 PDF 或來源確認留存於 `raw/papers/`。
2. **深度精讀**：完整解析論文之問題意識、法律爭點、實證數據與法理結論。
3. **建立論文精讀筆記**：在 `wiki/papers/` 建立對應的 Markdown 文件，嚴格遵守第 5 節的「論文精讀模板」。
4. **滾雪球連動更新（Cascade Updating - 核心關鍵）**：
   單篇論文入庫時，**必須主動連動檢查並更新 3～8 個現有或新增的 Wiki 頁面**：
   - 若論文涉及具體法規（如證交法第20條之1、歐盟 MiCA），更新或建立 `wiki/regulations/` 中的對應頁面，將該論文的觀點加入其「重要文獻見解」段落。
   - 若論文探討核心法理概念（如「推計詐欺理論 Fraud-on-the-Market」），更新或建立 `wiki/concepts/` 頁面，豐富要件爭議與學者立場。
   - 若論文引述具體司法判決或裁罰，更新或建立 `wiki/cases/` 頁面。
   - **檢驗矛盾與前作修正**：若本論文質疑、推翻或改進了知識庫中已存在的另一篇論文（例如：論文 B 批評論文 A 的損害計算模型），**必須立即前往該前作頁面（`wiki/papers/論文A.md`），在「後續學說批判與發展」區塊中補上鏈結 `[[wiki/papers/論文B]]` 並簡述其批評重點**。
5. **更新總目錄**：在 `index.md` 對應分類中加入此論文的雙向鏈結與 1 句話核心摘要。
6. **寫入日誌**：在 `log.md` 追加一筆紀錄：
   ```markdown
   ## [YYYY-MM-DD] ingest | 《論文繁體標題》
   - 來源檔案：raw/papers/xxx.pdf
   - 關聯實體更新：[[wiki/regulations/xxx]], [[wiki/concepts/xxx]]
   - 前作連動：更新 [[wiki/papers/yyy]] 的批判章節
   ```
7. **向使用者回報**：以精簡條列說明本論文核心貢獻，並列出本次連動新增/修改的所有 Wiki 檔案。

---

### 作業二：專題查詢與知識回寫 (Query & Compounding)

當使用者針對金融法規提問或要求進行跨文獻比較時：

1. **檢索先行**：LLM 優先閱讀 `index.md` 與相關概念頁面定位知識脈絡，而非盲目從零猜測。
2. **回答規範**：
   - 引用觀點時一律標註來源篇名與章節。
   - 大量使用 Obsidian 雙向鏈結 `[[wiki/...]]` 指向知識庫既有條目。
3. **知識複利（回寫機制）**：
   - 當產出高價值的產出（如：「各國加密資產發行監理比較表」、「內線交易消息明確時點學說演進圖」、「修法建議綜述」），這些成果**嚴禁遺棄在對話歷史中**。
   - LLM 應將其整理為完整的 Markdown 頁面，儲存至 `wiki/synthesis/` 或 `wiki/comparisons/`。
   - 同步更新 `index.md` 與 `log.md`。

---

### 作業三：知識庫體檢與研究缺口發掘 (Lint & Health-Check)

定期或在使用者指示下，LLM 應對全庫執行「健康檢查」：

1. **孤島檢查（Orphan Pages）**：找出沒有任何其他頁面反向鏈結（Backlink）的孤立頁面，為其建立關聯。
2. **未落地概念（Missing Concept Entities）**：掃描多篇論文中頻繁提及、但尚未在 `wiki/concepts/` 建立專屬頁面的法理名詞，主動提議建立。
3. **學說矛盾審查（Doctrinal Conflicts）**：檢查庫內不同學者或裁判見解是否存在衝突未被標註的情況（如：多數說 vs. 少數說 vs. 實務見解）。
4. **時效過期檢視（Stale Claims）**：標註是否有因新法通過（如證券交易法最新修正案）而導致舊論文分析前提已失效的段落。
5. **發掘研究空白（Open Research Gaps）**：主動向使用者提出目前文獻庫中尚未被充分討論的跨領域空白，推薦下一步可鎖定的論文題目或關鍵字。
6. 檢查完成後於 `log.md` 追加記錄：`## [YYYY-MM-DD] lint | 全庫健康度檢核與缺口報告`。

## 6. 語法與雙向鏈結規範 (Linking Conventions)

1. **命名一致性**：
   - 避免同義詞分家：例如「重大消息明確時點」與「重大消息成立時點」，優先確認統一用詞，必要時使用 Alias（別名）指向同一 Markdown。
2. **Wikilinks 標準語法**：
   - 內部引用一律使用 `[[路徑/檔名|顯示名稱]]` 或 `[[檔名]]`。
   - 範例：`依據 [[wiki/regulations/證券交易法|證交法]] 第 20 條之規定...`。
3. **圖片與圖表引用**：
   - 論文內重要架構圖、統計圖表或投影片素材統一置於 `assets/`。
   - Markdown 內部以 `![圖表說明](../../assets/image_name.png)` 方式嵌入。
